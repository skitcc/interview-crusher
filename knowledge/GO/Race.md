# Гонки данных (Data Races) и Синхронизация

![[Pasted image 20260905234059.png]]

> [!DANGER] Что такое Data Race?
> **Data Race (гонка данных)** возникает, когда две или более горутины обращаются к одной и той же области памяти одновременно, при этом **как минимум одно обращение — это запись**, и между ними нет механизмов синхронизации.

---

## 1. Проблема: неатомарные операции

В примере ниже 1000 горутин пытаются одновременно инкрементировать общую переменную `money`.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	money := 0
	wg := &sync.WaitGroup{}

	wg.Add(1000)
	for range 1000 {
		go func() {
			defer wg.Done()
			money++
		}()
	}
	wg.Wait()
	fmt.Println(money)
}
```

### Почему здесь возникает гонка?
Операция `money++` кажется атомарной только на уровне языка. На уровне процессора и ассемблера она делится на **3 независимых этапа** (*Read-Modify-Write*):
1. **Чтение (Load):** прочитать текущее значение `money` из оперативной памяти в регистр процессора.
2. **Модификация (Increment):** прибавить единицу внутри регистра.
3. **Запись (Store):** записать обновленное значение обратно из регистра в оперативную память.

Если Горутина 1 и Горутина 2 прочитают значение `0` одновременно, обе прибавят к нему `1` и запишут в память `1`. В итоге вместо двух прибавлений произошло только одно — данные были затёрты.

> [!TIP] Детектор гонок (Race Detector)
> Чтобы компилятор помог выявить такие места, запускайте программу с флагом `-race`:
> ```bash
> go run -race main.go
> go test -race ./...
> ```
> Рантайм Go использует *ThreadSanitizer* и при первой же конкурентной записи выведет в терминал стек вызовов обеих конфликтующих горутин (`WARNING: DATA RACE`).

## 2. Решение через Атомики (sync/atomic)

Атомарные операции выполняются на аппаратном уровне процессора за один неделимый такт (через инструкции `LOCK XADD` / `CAS`). Никакая другая горутина или ядро процессора не могут вмешаться в середину выполнения этой операции.

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var money atomic.Int32
	wg := &sync.WaitGroup{}

	wg.Add(1000)
	for range 1000 {
		go func() {
			defer wg.Done()
			money.Add(1)
		}()
	}
	wg.Wait()
	fmt.Println(money.Load())
}
```

* **Плюсы:** самая высокая производительность для простых числовых счетчиков и флагов (не создают блокировок потоков ОС).
* **Минусы:** подходят только для базовых типов и простейших математических действий. Не подходят для защиты сложных блоков кода и составных структур.

## 3. Блокировки: Mutex и RWMutex

Когда нужно атомарно обновить сразу **несколько зависимых переменных** (например, инвариант `money == donations`), используют мьютексы.

### sync.RWMutex (Reader-Writer Mutex)
Обычный `sync.Mutex` блокирует данные полностью. `sync.RWMutex` разделяет блокировки на чтение и запись:
* **`RLock()` / `RUnlock()` (Read Lock):** множественный доступ. Несколько горутин-читателей могут читать память параллельно, не мешая друг другу.
* **`Lock()` / `Unlock()` (Write Lock):** эксклюзивный доступ. Писатель ждёт, пока уйдут все читатели. Пока писатель держит замок, ни читать, ни писать другие горутины не могут.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	money := 0
	donations := 0
	wg := &sync.WaitGroup{}
	mutex := &sync.RWMutex{}

	go func() {
		for {
			mutex.RLock()
			m := money
			d := donations
			mutex.RUnlock()

			if m != d {
				fmt.Println(m, d)
				break
			}
		}
	}()

	wg.Add(10)
	for range 10 {
		go func() {
			defer wg.Done()
			mutex.Lock()
			money++
			donations++
			mutex.Unlock()
		}()
	}
	wg.Wait()
}
```

> [!INFO] Инвариант согласованности
> В этом коде `m != d` внутри читателя никогда не выполнится, так как писатель обновляет обе переменные внутри одной критической секции `mutex.Lock()`. Читатель всегда видит либо состояние «до» добавления, либо «после».

## 4. Каналы (Channels)

Идиома Go: *"Не общайтесь, разделяя память. Разделяйте память, общаясь"*.  
Канал — это потокобезопасная очередь (`runtime.hchan`) со встроенным механизмом синхронизации и блокировок.

```go
package main

import "fmt"

func main() {
	ch := make(chan int)

	for i := range 5 {
		go func() {
			ch <- i + 1
		}()
	}

	for range 5 {
		go func() {
			val := <-ch
			fmt.Println(val)
		}()
	}
}
```

* **Особенности:**
  * Не требуется явный `sync.WaitGroup` для передачи данных: отправитель и получатель небуферизированного канала блокируются до тех пор, пока данные не будут переданы («рандеву»).
  * Порядок вывода значений в консоль недетерминирован — он зависит исключительно от работы планировщика Go (какая горутина первой получит квант времени процессора).
  * В этом `main` никто не ждёт горутины. Процесс может завершиться раньше, чем они успеют напечатать значения.

## 5. Практическая задача: подсчёт времени выполнения

**Задача:** Запустить 100 параллельных воркеров со случайной задержкой (`randomWait`), посчитать:
1. `totalSec` — сумма секунд, которые проспали все горутины.
2. `mainSec` — максимальное время выполнения одной горутины.

### Вариант А: Решение через Каналы

В этом паттерне `main` выступает единственным сборщиком результатов. Так как канал небуферизированный, ровно 100 отправок найдут 100 чтений, а гонка исключена конструктивно (нет общего состояния между воркерами).

```go
package main

import (
	"fmt"
	"math/rand"
	"time"
)

func randomWait() int {
	workSec := rand.Intn(5 + 1)
	time.Sleep(time.Duration(workSec) * time.Second)

	return workSec
}

func main() {
	mainSec, totalSec := 0, 0
	ch := make(chan int)

	for range 100 {
		go func() {
			ch <- randomWait()
		}()
	}

	for range 100 {
		sec := <-ch
		totalSec += sec
		mainSec = max(mainSec, sec)
	}

	fmt.Println("main : ", mainSec)
	fmt.Println("total : ", totalSec)
}
```

---

### Вариант Б: Решение через WaitGroup + Mutex

Здесь все воркеры параллельно выполняют тяжелую операцию `randomWait()`, но результат записывают в разделяемые переменные, защищая критическую секцию через `sync.Mutex`.

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"time"
)

func randomWait() int {
	workSec := (rand.Intn(5 + 1))
	time.Sleep(time.Duration(workSec) * time.Second)

	return workSec
}

func main() {
	var mainSec int = 0
	var totalSec int

	mutex := &sync.Mutex{}
	wg := &sync.WaitGroup{}

	for range 100 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			sec := randomWait()

			mutex.Lock()
			totalSec += sec
			mainSec = max(mainSec, sec)
			mutex.Unlock()
		}()
	}

	wg.Wait()
	fmt.Println("main : ", mainSec)
	fmt.Println("total : ", totalSec)
}
```

> [!WARNING] Важное правило размещения Mutex
> Вызов `randomWait()` **вынесен за пределы** `mutex.Lock()`. Блокировка удерживается лишь доли микросекунды — ровно на момент сложения. Если бы `randomWait()` был внутри замка, горутины выполнялись бы строго по очереди, убив параллельность.
