# Swiss tables

![[Pasted image 20260908201054.png]]

![[Pasted image 20260908201556.png]]

С Go 1.24 встроенная `map` реализована как Swiss Table (дизайн Abseil). Код живёт в `internal/runtime/maps`. Ниже устройство текущей `map`: что отвечать, когда спрашивают «как устроена мапа».

## Из чего состоит

Термины рантайма:

- **Slot** — одна пара ключ/значение.
- **Group** — 8 слотов и control word на 8 байт. Байт соответствует своему слоту.
- **Table** — одна swiss table: массив групп плюс счётчики заполненности.
- **Map** — directory таблиц. Старшие биты хеша выбирают таблицу.
- **H2** — младшие 7 бит хеша, лежат в control byte занятого слота.
- **H1** — старшие 57 бит, по ним выбирается группа внутри таблицы.

У занятого слота старший бит control byte сброшен, в младших семи лежит H2. Пустой слот и tombstone (удалённый) помечены старшим битом: проба обязана останавливаться на пустом и проходить сквозь tombstone.

Маленькая `map`, которая умещается в одну группу, directory не заводит: указатель смотрит прямо на эту группу.

## Поиск

1. Ключ хешируется.
2. По H1 выбирается стартовая группа.
3. Все 8 control byte группы сравниваются с нужным H2 за одну операцию. На amd64 для этого есть SIMD.
4. Слот, у которого H2 совпал, ещё раз сравнивается самим ключом. Семь бит дают ложное совпадение примерно в 1 случае из 128, поэтому сравнение ключа обязательно.
5. Если в группе нет ни совпадения, ни пустого слота, проба идёт дальше. Шаг квадратичный, последовательность треугольная: `h`, `h+1`, `h+1+2`, `h+1+2+3`, …

Проба заканчивается на группе, в которой есть пустой слот. Из-за этого таблица не бывает заполнена на 100%. В группе из 8 слотов под данные отведено не больше 7 (`maxAvgGroupLoad = 7`). Tombstone тоже занимает слот в этом бюджете: череда `delete` без вставок может довести таблицу до роста, хотя живых ключей мало.

## Удаление

Если в группе ещё есть пустой слот, удалённый помечают пустым. Если группа полная, ставят tombstone. Пустой слот посреди пробы оборвал бы поиск, и ключи дальше по последовательности перестали бы находиться. Вставка сначала занимает tombstone и только потом пустой слот. Окончательно tombstone вычищаются при росте таблицы.

## Рост

Последовательность пробы зависит от числа групп, поэтому одну table нельзя подрастить «на пару слотов»: её перестраивают целиком.

Чтобы рост большой `map` не был одной длинной паузой, map режется на несколько независимых таблиц (extendible hashing):

- индекс в directory — это `globalDepth` старших бит хеша;
- размер directory равен `1 << globalDepth`;
- несколько ячеек directory могут указывать на одну и ту же table, пока та не раскололась;
- одна table не растёт дальше `maxTableCapacity` = 1024 слотов. Дальше она делится на две, и растёт только затронутая половина пространства хешей.

Пока таблица одна и меньше этого предела, рост — замена на table вдвое большей ёмкости.

## Итерация

Порядок `range` по `map` не задан и специально случаен. Во время обхода:

- уже отданный ключ не приходит второй раз;
- ключ, добавленный во время обхода, может попасться, а может нет;
- изменение значения видно обходу;
- удалённый ключ больше не приходит.

Если table выросла в середине `range`, итератор продолжает идти по старой таблице (чтобы не отдать ключ дважды) и заново ищет каждый ключ в новой (чтобы увидеть `delete` и новое значение).

## Конкурентный доступ

Запись в `map` одновременно с другой записью или чтением роняет процесс:

```text
fatal error: concurrent map read and map write
```

Это не обычная гонка данных, после которой программа живёт дальше. Детектор `-race` такое тоже показывает, но падение даёт сам рантайм. Общую `map` закрывают `sync.Mutex` или `sync.RWMutex` на все операции, включая чтение. Либо у карты один владелец, а наружу уходят уже готовые значения — через канал, см. [[Race]].

## Ключи с указателями

Хеш указателя считается по его адресу. Стек горутины рантайм умеет переносить, и адрес стекового объекта тогда меняется. Поэтому объект, на который ссылается указатель внутри ключа, при записи в `map` убегает в кучу — даже если сама `map` со стека не уходит. См. [[Escape Analysis]].

## Как было до Go 1.24

Старая `map` — это `hmap` и бакеты `bmap` по 8 ключей. В бакете лежал `tophash` (старшие 8 бит хеша). Не поместившиеся пары уходили в overflow-бакет, отдельным куском памяти. Средняя заполненность бакета держалась около 6.5 из 8. Рост удваивал число бакетов и эвакуировал пары в новый массив.

Эту схему ещё спрашивают, если явно говорят «до 1.24» или «бакеты и overflow». В актуальном компиляторе её больше нет: поиск идёт группами Swiss Table, рост — дроблением directory, а не одной эвакуацией всей карты.
