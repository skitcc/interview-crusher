# Синхронизация горутин: Fork-Join Pattern и sync.WaitGroup

> [!ABSTRACT] Модель Fork-Join
> По умолчанию горутины в Go запускаются асинхронно («выстрелил и забыл»). 
> Паттерн **Fork-Join** предполагает две фазы:
> 1. **Fork:** родительская горутина порождает дочерние задачи (`go func()`).
> 2. **Join:** родительская горутина блокируется в точке ожидания, пока все дочерние горутины не завершат выполнение, и лишь затем продолжает работу.

---

## 1. Базовый пример с sync.WaitGroup

```go
package main

import (
	"fmt"
	"sync"
)

func foo(wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("foo")
}

func main() {
	wg := &sync.WaitGroup{}
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("in")
	}()
	wg.Add(1)
	go foo(wg)

	wg.Wait()
	fmt.Println("main")
}
```

### Вывод программы
Строка `main` **всегда** выводится последней, так как `wg.Wait()` блокирует горутину `main`. При этом порядок строк `in` и `foo` недетерминирован и определяется планировщиком Go:
```text
in      или     foo
foo             in
main            main
```

---

## 2. Как устроен sync.WaitGroup под капотом

Внутри `sync.WaitGroup` находится атомарный 64-битный счётчик и семафор:
* **`wg.Add(delta int)`:** увеличивает счётчик активных задач на `delta`.
* **`wg.Done()`:** уменьшает счётчик на 1 (под капотом это просто вызов `wg.Add(-1)`).
* **`wg.Wait()`:** переводит текущую горутину в состояние сна (`gopark`), пока внутренний счётчик не опустится ровно до `0`. Как только счётчик обнуляется, рантайм будит ожидающую горутину через семафор.

> [!TIP] Использование `defer wg.Done()`
> Вызов `wg.Done()` всегда стоит заворачивать в `defer` в первой строчке горутины. Если внутри горутины случится паника или ранний `return`, счётчик всё равно гарантированно уменьшится, и программа не зависнет в вечном ожидании (`deadlock`).

---

## 3. Почему `WaitGroup` передают строго по указателю (`*sync.WaitGroup`)?

В функции `foo(wg *sync.WaitGroup)` передача идёт по ссылке (указателю). 

> [!DANGER] Ошибка копирования (Pass by value)
> Если убрать звёздочку и объявить функцию как `func foo(wg sync.WaitGroup)`:
> 1. В функцию передастся **полная копия структуры** со своим независимым счётчиком.
> 2. `wg.Done()` внутри `foo` уменьшит счётчик копии, а оригинальный `wg` в `main` так и останется со значением `> 0`.
> 3. В точке `wg.Wait()` программа зависнет навсегда:  
>    `fatal error: all goroutines are asleep - deadlock!`

В структуре `sync.WaitGroup` есть специальное скрытое поле `noCopy`. Линтер `go vet` автоматически отслеживает такие структуры и выдает предупреждение при попытке передать их по значению:
```bash
go vet main.go
# foo passes lock by value: sync.WaitGroup contains sync.noCopy
```

---

## 4. Золотое правило: где вызывать `wg.Add()`?

`wg.Add()` **всегда вызывается в родительской горутине ДО оператора `go`**.

❌ **Неправильно:**
```go
go func() {
    wg.Add(1) // ОШИБКА: гонка между main и горутиной!
    defer wg.Done()
    // ...
}()
wg.Wait()
```
*Если `main` дойдёт до `wg.Wait()` раньше, чем дочерняя горутина успеет вызваться и сделать `Add(1)`, счётчик в `Wait()` будет равен `0`, и `main` мгновенно завершит всю программу.*

---

## 5. Всегда ли нужно синхронизировать горутины?

**Нет, не всегда.** Не все горутины требуют `Join` перед завершением `main`.

### Когда синхронизация через WaitGroup НЕ нужна:
1. **Фоновые демоны (Background / Daemon workers):**
   * Периодический сброс метрик раз в минуту (`ticker`).
   * Heartbeat-сигналы в Consul / etcd.
   * Очистка протухшего кеша в памяти.
2. **Fire-and-forget задачи:**
   * Неблокирующая отправка аналитики или аудит-лога во внешнюю очередь (Kafka / RabbitMQ), потеря которых не критична для текущего запроса.

### Чем управляют несинхронизированными горутинами?
Вместо `WaitGroup` для фоновых задач чаще используют **`context.Context`**:
* При выключении приложения (`graceful shutdown`) контекст отменяется (`ctx.Done()`), и долгоживущие фоновые горутины корректно закрывают сокеты и файлы перед выходом.
