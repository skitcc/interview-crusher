# Escape Analysis (Анализ побега) в Go

**Escape Analysis (анализ побега)** — этап компиляции, на котором компилятор решает, где выделить память под переменную: на **стеке** или в **куче**.

* **Стек:** Выделение памяти сводится к смещению указателя стека (одна инструкция CPU). Память очищается мгновенно при выходе из функции. Бесплатно для Garbage Collector (GC).
* **Куча:** Выделение через аллокатор рантайма. Требует поиска свободного слота памяти, учета в метаданных и последующей очистки сборщиком мусора (GC).

---

## 1. Когда переменные выделяются в куче

1. **Указатель уходит вверх (возврат из функции):**  
   Когда на локальную переменную продолжают ссылаться после завершения текущего стекового фрейма (`return &x`).
2. **Значение слишком большое для стека:**  
   Явная переменная (`var x T`) крупнее `MaxStackVarSize` уходит в кучу. С Go 1.24 это **128 КБ** (до этого лимит был 10 МБ).  
   Неявная аллокация — `make([]T, n)`, `new(T)`, `&T{}` — ограничена жёстче: `MaxImplicitStackVarSize` = **64 КБ**. `make([]byte, 64*1024+1)` уже в куче, даже если слайс из функции не убегает.
3. **Размер значения неизвестен при компиляции:**  
   Динамические срезы, размер которых вычисляется во время исполнения: `make([]T, n)`, где `n` — переменная.
4. **Захват переменной в замыкание (Closure):**  
   Если анонимная функция захватывает переменную внешнего скоупа и переживает породивший её контекст (возвращается наружу или уходит в `go func()`).
5. **Отправка указателя в канал (`ch <- &x`):**  
   Компилятор не может статически гарантировать, какая горутина и когда прочитает эти данные.
6. **Упаковка в интерфейс (`any` / `eface`):**  
   Если значение приводится к интерфейсу и передается в функцию, внутренности которой компилятор не может полностью заинлайнить (например, `fmt.Println`).
7. **Запись в `map` ключа, внутри которого есть указатель:**  
   Объект, на который ссылается этот указатель, убегает в кучу, даже если сама `map` остаётся на стеке. Хеш указателя считается по адресу, а стек горутины рантайм умеет переносить. См. [[Swiss tables]].

## 2. Ментальная модель: Указатель вниз vs Указатель вверх

```text
Стек вызовов:
┌──────────────┐
│    main()    │  ◄── Живет долго
└──────┬───────┘
       │
    (Указатель ВНИЗ: &a)         (Указатель ВВЕРХ: &b)
    Передали в inc(&a)           Вернули из double()
       │                                   ▲
       ▼                                   │
┌──────────────┐                           │
│   callee()   │  ─────────────────────────┘ (Фрейм уничтожается при return!)
└──────────────┘
```

* **Указатель вниз (`callee(&x)`):**  
  Стек вызывающей функции живет **дольше**, чем вызываемой. Память выделена в вызывающем фрейме, затирания нет.  
  👉 **Переменная остается на стеке.**
* **Указатель вверх (`return &x`):**  
  Стек вызываемой функции будет **уничтожен** в момент `return`. Оставить переменную на стеке нельзя — возникнет висячий указатель (dangling pointer) на мусор.  
  👉 **Компилятор перемещает переменную в кучу (`moved to heap`).**

## 3. Замыкания (Closures) и Escape Analysis

> [!ABSTRACT] Определение
> **Замыкание (Closure)** — это анонимная функция, которая связывается с переменными из своего **лексического окружения** (внешней функции) и продолжает иметь к ним доступ даже после того, как внешняя функция завершила работу.

### Почему все внешние переменные берутся по указателям?
Замыкание должно разделять **ту же самую ячейку памяти**, что и внешняя функция (семантика общего состояния, а не моментального снимка). Если замыкание или внешняя функция изменят значение переменной, обе стороны обязаны увидеть это изменение:

```go
func counter() func() int {
    x := 0
    return func() int {
        x++ // Замыкание мутирует внешнюю переменную!
        return x
    }
}
```

### Как компилятор реализует это под капотом:
1. Компилятор не может просто скопировать значение `x`, иначе вызов `x++` не сохранялся бы между запусками функции.
2. Компилятор неявно генерирует структуру контекста (окружение замыкания), в которую помещает **указатель** на внешнюю переменную:
   ```go
   // Псевдокод компилятора:
   type closureContext struct {
       F  uintptr // адрес кода функции
       x  *int    // УКАЗАТЕЛЬ на захваченную переменную!
   }
   ```
3. **Момент побега (Escape):**  
   Когда функция `counter()` завершается, её стековый фрейм уничтожается. Если бы переменная `x` осталась на стеке `counter()`, указатель `*int` внутри замыкания стал бы указывать на мусор (dangling pointer).  
   Компилятор видит, что **указатель на переменную уходит вверх вместе с возвращаемым замыканием**, и принудительно переносит `x` в кучу (`moved to heap: x`).

> [!NOTE] Случай без побега (Инлайнинг)
> Если замыкание вызывается тут же на месте и никуда не передается:
> ```go
> func run() {
>     x := 10
>     func() { x++ }() // Вызов сразу
> }
> ```
> Компилятор инлайнит анонимную функцию, время жизни `x` не превышает фрейм `run()`, и `x` **остается на стеке**.

## 4. Роль инлайнинга и интерфейса `eface`

### Инлайнинг (Inlining)
Подстановка тела функции напрямую в место ее вызова вместо инструкции `CALL`.  
* **Зачем для Escape Analysis:** Устраняет непрозрачные границы функций. Компилятор видит полный жизненный цикл переменной и часто оставляет на стеке то, что иначе ушло бы в кучу.

### Интерфейс `eface` (`any`)
Пустой интерфейс внутри рантайма устроен как структура из двух указателей (`src/runtime/runtime2.go`):
```go
type eface struct {
    _type *_type         // Метаданные о типе
    data  unsafe.Pointer // УКАЗАТЕЛЬ на данные
}
```
Поле `data` обязано быть адресом в памяти (для корректной работы GC).  
При упаковке значения в интерфейс вызываются функции рантайма (`runtime.convT*`), которые выделяют под него память. Если вызываемая функция (как `fmt.Println`) не может быть заинлайнена до конца, компилятор консервативно аллоцирует это значение в куче.

## 5. Практический пример и разбор вывода компилятора

### Код:
```go
package main

import "fmt"

func inc(a *int) {
    *a++
}

func double(a *int) *int {
    b := 2 * *a
    return &b
}

func main() {
    a := 42
    inc(&a)
    c := double(&a)
    fmt.Println(*c)
}
```

### Команда анализа:
```bash
go build -gcflags="-m" main.go
```

### Разбор вывода компилятора:

```text
./main.go:5:6: can inline inc
./main.go:9:6: can inline double
./main.go:17:5: inlining call to inc
./main.go:18:13: inlining call to double
./main.go:19:13: inlining call to fmt.Println
```
* Обе функции (`inc`, `double`) и обертка `fmt.Println` достаточно просты, чтобы компилятор встроил их тела в `main`.

```text
./main.go:5:10: a does not escape
./main.go:9:13: a does not escape
```
* Передача `&a` идет **вниз по стеку**. Компилятор убедился, что указатель не сохраняется в глобальные переменные. Переменная `a` остается на стеке `main`.

```text
./main.go:10:2: moved to heap: b
```
* Функция `double` возвращает `&b` (**указатель вверх**). Компилятор помечает `b` как сбежавшую в кучу уже на этапе сигнатуры функции, защищая память от уничтожения стекового фрейма.

```text
./main.go:19:13: ... argument does not escape
```
* Слайс `[]any`, неявно созданный под аргументы вариативной функции `fmt.Println(...)`, не покидает скоуп `main` и размещается на стеке.

```text
./main.go:19:14: *c escapes to heap
```
* Разыменованное значение `*c` передается в аргумент типа `any`. Из-за невозможности полностью заинлайнить глубокие недра пакета `fmt` (рефлексия, буферы вывода), упакованное значение боксится в кучу.

## 6. Чек-лист для запоминания

1. **Корректность важнее производительности:** Компилятор всегда предпочтет кучу, если нет 100% гарантии безопасности стека.
2. **Стек — привилегия, а не норма:** Переменная остается на стеке только тогда, когда доказано, что к ней не будет обращений после выхода из функции.
3. **Указатель вниз = Стек:** Передача адреса в аргументы почти всегда безопасна.
4. **Указатель вверх = Куча:** Возврат адреса через `return` почти гарантированно приводит к аллокации в куче.
5. **Замыкание держит указатели:** Переменные внешнего скоупа захватываются по ссылке через скрытую структуру контекста; если замыкание переживает родительскую функцию — переменные уходят в кучу.
6. **Интерфейсы лишают гарантий:** Передача значений в `any` внутри неинлайнящихся функций ведет к аллокации памяти в куче.
7. **Два лимита размера:** явная переменная до 128 КБ может жить на стеке, `make` / `new` / `&T{}` — до 64 КБ. Сверх лимита компилятор сразу выбирает кучу, чтобы не раздувать стек горутины.
