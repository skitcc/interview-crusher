# Внутреннее устройство Go: Модель GMP, Планировщик, Netpoller и Handoff

![[Pasted image 20260922215253.png]]

## 1. Базовые сущности GMP
* **G (Goroutine):** Легковесный поток выполнения. Имеет собственный стек (от 2 КБ), программный счетчик (PC) и статус (`_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gsyscall`).
* **M (Machine):** Реальный поток операционной системы (OS Thread). Создается через `clone()` в Linux. Исполняет инструкции на физическом ядре CPU.
* **P (Processor):** Логический контекст / ресурс выполнения. Количество `P` строго ограничено `GOMAXPROCS`. Содержит **локальную очередь задач (LRQ)** и кэш аллокатора памяти (`mcache`).

> [!important] Главное правило
> Чтобы поток **M** мог выполнять Go-код горутины **G**, он **обязан захватить процессор P**. Без `P` код исполняться не может (исключение — системный поток `sysmon`).

## 2. Иерархия очередей и алгоритм Work-Stealing

Планировщик распределяет задачи через двухуровневую систему очередей:
1. **LRQ (Local Run Queue):** Локальная очередь у каждого `P`. Вмещает до **256 горутин**. Доступ к ней не требует глобальных блокировок (быстро и без конфликтов кэшей CPU).
2. **GRQ (Global Run Queue):** Глобальная очередь в разделяемой памяти рантайма (`sched.runq`). Защищена глобальным мьютексом. Туда попадают горутины, не поместившиеся в LRQ, или проснувшиеся системные задачи.

```text
       ┌───────────────────────────────┐
       │   Global Run Queue (GRQ)      │
       └──────────────┬────────────────┘
                      │ (проверка каждые 61 такт)
       ┌──────────────┴───────────────┐
       ▼                              ▼
┌──────────────┐               ┌──────────────┐
│  P0 (LRQ)    │◄───(Steal)────┤  P1 (LRQ)    │
└──────┬───────┘ (украсть 50%) └──────┬───────┘
       │                              │
    [ M0 ]                         [ M1 ]

```

### Алгоритм поиска работы (функция `findrunnable`):
Когда поток `M` на процессоре `P` освобождается, он ищет новую горутину в строгом порядке:

1. **Правило 1/61 тика:**  
   Каждый **61-й такт планировщика** (`schedtick % 61 == 0`) поток `M` **принудительно** идет в глобальную очередь (GRQ), минуя свою локальную.  
   *Зачем:* Чтобы горутины в глобальной очереди не голодали (Starvation Protection), если локальные очереди бесконечно забиты работой. Из GRQ забирается пачка (батч) горутин: $\min(len(GRQ), 256 / GOMAXPROCS + 1)$.
2. **Своя LRQ:** Если это не 61-й шаг, забирается задача из локальной очереди текущего `P`.
3. **Глобальная очередь (GRQ):** Если своя LRQ пуста — проверяется GRQ (под замком).
4. **Network Poller:** Проверяются проснувшиеся сетевые сокеты.
5. **Work Stealing (Кража работы):** Если всё еще пусто, поток выбирает случайный другой процессор `P2` и **крадет половину его локальной очереди** (50% задач).
6. Если работы вообще нигде нет — поток `M` отпускает `P` и уходит спать в `sched.midle`.

## 3. Network Poller против File I/O: почему разное поведение?

```go
func main() {
    buf := make([]byte, 10)
    
    // 1. БЛОКИРУЕТ поток ОС:
    file, _ := os.Open("file.txt")
    dataLoc, _ := file.Read(buf)
    
    // 2. НЕ БЛОКИРУЕТ поток ОС:
    conn, _ := net.Dial("tcp", "example.com:80")
    dataNet, _ := conn.Read(buf)
}
```

### Почему сеть не блокирует тред:
1. Сетевые сокеты в Go по умолчанию помечены флагом **`O_NONBLOCK`**.
2. При вызове `conn.Read()` ядро Linux не усыпляет тред, а мгновенно возвращает ошибку **`EAGAIN`** («данных нет, зайди позже»).
3. Рантайм ловит `EAGAIN`, регистрирует сокет в системном опросщике (**`epoll`** в Linux) и переводит горутину в статус `_Gwaiting` (**паркует в Netpoller**).
4. **Поток M свободен!** Он тут же берет следующую горутину из очереди `P`.
5. Когда ядро сообщает о готовности данных:
   * Поток `M` при поиске работы забирает горутину из netpoller;
   * Либо системный монитор (`sysmon`) забирает проснувшиеся горутины и переносит их в GRQ.

### Почему файлы на диске блокируют тред:
* **Ограничение ядра Linux:** интерфейс `epoll` **не поддерживает работу с обычными файлами** на диске (дескриптор файла всегда считается «готовым к чтению»).
* Поэтому чтение файла — это честный, синхронный системный вызов ядра. Поток `M` засыпает в пространстве ядра (состояние Uninterruptible Sleep / `D`).
* Чтобы программа не зависла, здесь спасает механизм **Handoff**.

## 4. Системный монитор (`sysmon`)

`sysmon` — это специальный поток ОС (`M`), запускаемый при старте программы.
* **Работает БЕЗ процессора P:** на него не распространяется `GOMAXPROCS`.
* Засыпает динамически: от 20 мкс до 10 мс.

### Обязанности `sysmon`:
1. **Предотвращение сетевого голодания:** Если `netpoller` не опрашивался дольше 10 мс, `sysmon` сам вызывает `netpoll(0)` и вбрасывает проснувшиеся горутины в глобальную очередь (`injectglist`).
2. **Асинхронное вытеснение (Preemption):** Если горутина крутится на процессоре `P` дольше 10 мс без ухода в I/O (например, тяжелый цикл `for {}`), `sysmon` отправляет потоку сигнал **`SIGURG`**, принудительно переключая контекст на другую горутину.
3. **Принудительный Handoff (`retake`):** Если поток `M` застрял в системном вызове дольше 20 мкс, `sysmon` отбирает у него процессор `P`.

## 5. Механизм Handoff (`handoffp`)

**Handoff** — это передача процессора `P` (и всей его очереди) от застрявшего потока `M` другому системному потоку.

```text
[ Горутина G1 ] делает unix.Read(unix.Stdin)
      │
      ▼
Поток M1 засыпает в блокирующем вызове ядра
      │
      ▼
Handoff: P отстегивается от M1 (handoffp)
      │
      ├──> Находится спящий M2 (или создается новый через clone())
      └──> M2 забирает P и продолжает крутить остальные горутины
```

### Эксперимент: 10 горутин на Stdin при GOMAXPROCS=5

```go
func main() {
    runtime.GOMAXPROCS(5)

    for range 10 {
        go func() {
            var buf [1]byte
            unix.Read(unix.Stdin, buf[:]) // Прямой блокирующий сисколл ядра
        }()
    }

    time.Sleep(1 * time.Minute)
}
```

### Почему на выходе ровно 12 тредов ОС?
`GOMAXPROCS` ограничивает только количество одновременно исполняемого Go-кода, но **не ограничивает число потоков, спящих в сисколлах ядра**.

1. **10 потоков ОС:** каждая из 10 горутин вызвала `unix.Read`. Сработал Handoff: `P` каждый раз отбирался и создавался/будился новый поток `M`. В итоге 10 потоков `M` намертво заблокированы в ядре на чтении `Stdin`.
2. **1 поток (`sysmon`):** системный монитор, работающий всегда.
3. **1 рабочий поток (`m0` / worker):** поток, на котором горутина `main` завершила цикл и уснула на `time.Sleep`.

Итого: **$10 + 1 + 1 = 12$ системных потоков.**

## 6. Чтение и анализ Schedtrace (`GODEBUG=schedtrace=1000`)

### Расшифровка полей лога:
* `gomaxprocs=N`: количество доступных логических контекстов `P`.
* `threads=N`: общее число созданных потоков ОС `M` (счетчик `mcount`).
* `idlethreads=N`: потоки `M`, которые сейчас спят без работы.
* `idleprocs=N`: процессоры `P`, у которых нет задач.
* `runqueue=N`: количество горутин в **глобальной очереди (GRQ)**.
* `[ X Y Z ... ]`: размеры **локальных очередей (LRQ)** каждого конкретного процессора `P`.
* `schedticks=[ ... ]`: счетчик переключений горутин на каждом `P`.

---

### Кейс 1: 256 горутин с CPU-циклом на `GOMAXPROCS=2`

```go
func main() {
    runtime.GOMAXPROCS(2)
    for range 256 {
        go func() {
            for {
                for i := range 10000000 { _ = i * i }
            }
        }()
    }
    time.Sleep(1 * time.Minute)
}
```

```text
SCHED 0ms: gomaxprocs=20 idleprocs=17 threads=5 ... runqueue=0 [ 1 0 0 ... 0 ]
SCHED 1005ms: gomaxprocs=2 idleprocs=0 threads=5 idlethreads=2 runqueue=98 [ 152 4 ] schedticks=[ 52 50 ]
SCHED 2008ms: gomaxprocs=2 idleprocs=0 threads=5 idlethreads=2 runqueue=141 [ 103 10 ] schedticks=[ 102 100 ]
SCHED 3009ms: gomaxprocs=2 idleprocs=0 threads=5 idlethreads=2 runqueue=155 [ 55 44 ] schedticks=[ 151 149 ]
```

#### Разбор лога:
1. **`threads=5, idlethreads=2`:**  
   Всего создано 5 тредов (инициализировались еще при старте программы на 20-ядерном CPU).  
   * Активно работают ровно $5 - 2 - 1 (sysmon) = \mathbf{2}$ **потока**, так как `gomaxprocs=2`.  
   * 2 потока спят (`idlethreads=2`).
2. **Распределение задач:**
   * `runqueue=98` — 98 задач ждут в **глобальной очереди (GRQ)**.
   * `[ 152 4 ]` — в LRQ процессора `P0` лежит 152 горутины, в LRQ процессора `P1` — 4 горутины.
   * Сумма: $98 + 152 + 4 = 254$ задачи (+ 2 выполняются прямо сейчас на CPU = ровно наши **256 горутин**).
3. **`schedticks=[ 52 50 ] -> [ 102 100 ]`:**  
   Счетчики тиков растут синхронно (+50 тиков в секунду на ядро). Это доказывает работу **асинхронного вытеснения**: `sysmon` каждые 10–20 мс прерывает плотный цикл `_ = i * i` и ротирует задачи.
4. **Судьба `main`:**  
   Горутина `main` не имеет выделенного треда. Вызвав `time.Sleep`, она отдала свой `P` и перешла в `_Gwaiting`. Вычисления выполняются на обоих `P` на общих основаниях.

```

#### Разбор лога:
1. `threads=21, idlethreads=0`: Создан 21 системный поток (20 рабочих `M` под каждый `P` + 1 поток `sysmon`). Спящих тредов нет — все ядра утилизированы на 100%.

3. Остаток (138 задач) ожидает разгрузки в глобальной очереди `runqueue=138`.

## 7. Полная архитектурная схема планировщика

![[Pasted image 20260922232430.png]]

### Краткий чек-лист работы системы:
1. Новая горутина `go func()` пытается лечь в локальную очередь `LRQ` текущего `P`. Если LRQ полна (>256) — половина сбрасывается в `GRQ`.
2. Поток `M` берет задачи из своего `P`. Каждые 61 раз проверяет `GRQ`.
3. При сетевом I/O горутина уходит в `Netpoller` (сокет в `epoll`), поток `M` не блокируется.
4. При дисковом I/O поток `M` блокируется в ядре, срабатывает `handoffp`, освобождая `P` для других горутин.
5. Зависшие циклы и сокеты страхует фоновый `sysmon`, вбрасывая задачи обратно в очереди и вытесняя их сигналами `SIGURG`.
```
