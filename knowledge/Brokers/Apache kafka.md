## 1. Push vs Pull модель

В брокерах сообщений принципиально различают два подхода к доставке данных:

| Модель   | Кто управляет потоком?                                | Плюсы                                                                                                                                                                         | Минусы                                                                                                                                      | Где используется |
| :------- | :---------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------ | :--------------- |
| **Push** | **Брокер** сам «выталкивает» данные в консьюмера      | Минимальная задержка (сообщение улетает сразу при поступлении).                                                                                                               | **Риск перегрузки консьюмера (OOM)**, если продюсер строчит быстрее, чем воркер успевает переваривать. Нужен сложный механизм backpressure. | **RabbitMQ**     |
| **Pull** | **Консьюмер** сам запрашивает данные пачками (`poll`) | **Естественный Backpressure:** консьюмер берет столько, сколько может обработать. Идеально для батчинга (пакетной обработки). Легко перечитать старые данные (rewind offset). | Потенциальный оверхед на пустые опросы (решается через long-polling: `poll(timeout)` ждет появления данных на брокере).                     | **Apache Kafka** |

> [!info] Как это устроено в Kafka
> * **Producer $\to$ Broker:** модель **Push**. Продюсер берет батч сообщений и сам отправляет его в конкретный брокер.
> * **Consumer $\leftarrow$ Broker:** модель **Pull**. Консьюмер сам вызывает метод `poll()`, забирая пачку сообщений из лога партиции.

## 2. Лидеры партиций (Partition Leaders & Followers)

Каждый топик в Kafka делится на **партиции** (для параллелизма). Для надежности каждая партиция копируется на несколько брокеров. 

Среди этих копий роли четко разделены:
* **Leader (Лидер):** 
  * Ровно **одна нода-лидер** на партицию.
  * **Принимает все операции записи** от продюсеров.
  * По умолчанию отдает все операции чтения консьюмерам *(начиная с KIP-392 консьюмеры могут читать из ближайших реплик для снижения кросс-ДЦ трафика, но пишет всегда только Лидер)*.
* **Followers (Последователи / Реплики):**
  * Пассивные ноды. Они **не принимают клиентские записи**.
  * Ведут себя как обычные консьюмеры: непрерывно запрашивают (fetch) у Лидера новые данные и дописывают их в свой локальный лог.
  * Если Лидер падает, один из Followers становится новым Лидером.

## 3. Репликация и надежность данных

Репликация контролируется параметром **Replication Factor (RF)** (в проде обычно $RF = 3$).

### Понятие ISR (In-Sync Replicas)
Не все фолловеры одинаково полезны. Некоторые могут зависнуть или отстать по сети.
* **ISR (In-Sync Replicas)** — это подмножество реплик, которые **не отстают от лидера** (укладываются в таймаут `replica.lag.time.max.ms`, по умолчанию 30 сек).
* Если фолловер завис и не шлет fetch-запросы, Лидер **выкидывает его из списка ISR**.
* При падении Лидера новым Лидером может стать **только нода из списка ISR** *(если не включен опасный параметр `unclean.leader.election.enable=true`, чреватый потерей данных)*.

### Смещение и фиксация: HW vs LEO
* **LEO (Log End Offset):** смещение последней записи, которая физически записана на диск данной ноды (у лидера LEO всегда выше или равен).
* **HW (High Watermark):** максимальное смещение, которое **успели скопировать ВСЕ реплики из ISR**.
  > ⚠️ **Консьюмеры имеют право читать данные только до уровня High Watermark!** Пока данные не отреплицированы в ISR, клиент их не увидит. Это защищает от чтения данных, которые могут пропасть при падении лидера.

### Триада гарантированной доставки (Связка параметров)
Чтобы Kafka **никогда не теряла подтвержденные сообщения**, в проде используют связку:
1. `acks=all` (или `-1`) на Продюсере: продюсер ждет подтверждения от Лидера и всех ISR.
2. `replication.factor=3` на Топике: три физические копии данных.
3. `min.insync.replicas=2` на Брокере/Топике: если в ISR остался только один Лидер (две реплики упали), Лидер **откажется принимать новые записи** и вернет продюсеру ошибку `NotEnoughReplicasException`, вместо того чтобы рисковать потерей данных.

## 4. Что еще важно знать про Kafka (Бонус от автора)

### 1. Почему Kafka пишет на диск быстрее, чем другие в память?
Секрет бешеной производительности Kafka (миллионы сообщений в секунду):
* **Sequential I/O (Последовательная запись):** Запись в Kafka — это `append-only log` (дозапись в конец файла). Скорость последовательной записи на современный HDD/SSD сопоставима со скоростью работы памяти, так как головке диска не нужно метаться по секторам.
* **Page Cache ОС:** Kafka не держит сообщения в хипе JVM (чтобы не перегружать Garbage Collector). Она полностью полагается на кэш страниц операционной системы Linux.
* **Zero-Copy:** При передаче данных консьюмеру ядро Linux использует системный вызов `sendfile()`. Байты копируются с диска (Page Cache) **напрямую в сетевой сокет**, минуя User Space приложения. Процессор и память Kafka вообще не трогают полезную нагрузку.

```
Классический путь: Диск -> Page Cache -> Память приложения -> Буфер сокета -> Сеть (4 копирования, 4 context switch)
Zero-Copy (Kafka): Диск -> Page Cache ------------------------------> Сеть (2 копирования, 0 в user space!)
```

### 2. Log Compaction (Компактизация лога)
По умолчанию старые сообщения удаляются по времени (`retention.ms`, например, через 7 дней). 
Но топик можно перевести в режим `cleanup.policy=compact`:
* Kafka гарантирует сохранение **только последнего актуального значения для каждого ключа** (`message.key`).
* Все предыдущие значения с тем же ключом фоново удаляются компрессором.
* *Где применяется:* хранение текущего среза состояния сущностей (например, таблица актуальных балансов пользователей или остатков товаров).

### 3. Отказ от ZooKeeper $\to$ KRaft (Kafka Raft Metadata)
Раньше метаданными кластера и выбором контроллера управлял внешний ZooKeeper. Начиная с версии 3.x (и полностью в 4.0), ZooKeeper выпилен. Теперь метаданные кластера хранятся в специальном внутреннем топике, а ноды используют собственный алгоритм консенсуса **KRaft (Kafka Raft)**. Это резко ускорило восстановление при сбоях и сняло лимит на миллионы партиций.
