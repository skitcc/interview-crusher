## 1. Жизненный цикл TCP-соединений: `listen`, `accept` и 4-Tuple

### Демультиплексирование: почему порт сервера один, а клиентов много
TCP-порт (например, `443`) **не резервируется** под одного клиента. Серверное соединение идентифицируется в ядре не портом, а **квартетом (4-Tuple)**:
$$\text{Socket Key} = \{\text{Source IP}, \text{Source Port}, \text{Destination IP}, \text{Destination Port}\}$$

Поскольку у каждого клиента (или вкладки браузера) свой исходящий IP или эфемерный порт (`Source Port`), значение 4-Tuple всегда уникально. По нему ядро находит нужный сокет в глобальной хэш-таблице `tcp_hashinfo` за $O(1)$.

---

### Разделение сокетов: Слушающий vs Сокет соединения

```
1. socket() -> bind(:443) -> listen()
   [Слушающий сокет: listen_fd] ── ждет входящие SYN
                                        │
2. TCP 3-way handshake завершен        │
                                        ▼
3. accept(listen_fd) ─────────────> [Сокет соединения: client_fd]
                                    Привязан к конкретному 4-Tuple.
                                    listen_fd остается свободен для новых SYN.
```

1. **`listen(listen_fd, backlog)`:** переводит сокет в пассивный режим и выделяет в ядре две очереди:
   * **SYN Queue (Incomplete Connection Queue):** хранит полуоткрытые соединения (клиент прислал `SYN`, сервер ответил `SYN-ACK`, ждет финальный `ACK`).
   * **Accept Queue (Complete Connection Queue):** соединения, успешно завершившие 3-way handshake (`ESTABLISHED`), но еще не забранные приложением.
2. **`accept(listen_fd)`:** 
   * Достает готовое соединение из **Accept Queue**.
   * Создает в ядре **новый экземпляр сокета** и выделяет для процесса новый файловый дескриптор (`client_fd`).
   * Исходный `listen_fd` не меняет состояния и продолжает принимать новые подключения.

## 2. Анатомия сокета в ядре Linux

Сокет в Linux — это не файл на диске, а набор связанных структур данных в оперативной памяти ядра (RAM).

```
VFS: struct socket
       │
       ▼
Сетевой стек: struct sock
       │
       ▼
Транспортный уровень: struct tcp_sock
```

### Ключевые поля структур ядра

```c
/* include/net/sock.h */
struct sock {
    // 1. Очереди пакетов (двусвязные списки struct sk_buff)
    struct sk_buff_head   sk_receive_queue; // Буфер приема (SO_RCVBUF)
    struct sk_buff_head   sk_write_queue;   // Буфер отправки (SO_SNDBUF)

    // 2. Механизм ожидания
    wait_queue_head_t    *sk_sleep;         // Список процессов/epoll, ждущих этот сокет

    // 3. Коллбэки ядра на события
    void (*sk_data_ready)(struct sock *sk);  // Вызывается ядром при поступлении данных
    void (*sk_write_space)(struct sock *sk); // Вызывается при освобождении места для записи
};
```

```c
/* include/net/tcp.h */
struct tcp_sock {
    struct inet_sock      inet;       // IPv4/IPv6 метаданные (адреса, порты)

    // Состояние протокола
    u32    rcv_nxt;                   // Следующий ожидаемый Sequence Number
    u32    snd_una;                   // Самый старый неподтвержденный Seq (ждем ACK)

    // Управление потоком (Flow Control)
    u32    rcv_wnd;                   // Наше окно приема (сообщается удаленной стороне)
    u32    snd_wnd;                   // Окно приема удаленной стороны
    u32    snd_cwnd;                  // Congestion Window (окно перегрузки сети)
};
```

### Поведение буферов:
* **Буфер отправки (`sk_write_queue`):** вызов `write(fd, buf, len)` только копирует байты из User Space в `sk_write_queue` и возвращает управление. Данные удаляются из памяти ядра **только после получения `TCP ACK`** от клиента.
* **Буфер приема (`sk_receive_queue`):** ядро сохраняет входящие сегменты, сортирует их по `Seq` номерам и держит до тех пор, пока приложение не вызовет `read()`.

## 3. Путь входящего пакета: от NIC до сокета

```
1. Физическая среда -> Сетевая карта (NIC)
   └── NIC через DMA (Direct Memory Access) пишет пакет в Rx Ring Buffer (память RAM)
   └── NIC посылает Hardware IRQ процессору

2. CPU -> HardIRQ Handler
   └── Глушит прерывания карты (NAPI)
   └── Планирует SoftIRQ (демон ksoftirqd / NET_RX_SOFTIRQ)

3. Ядро: SoftIRQ
   └── Выгребает пакеты из памяти через poll() драйвера
   └── Формирует struct sk_buff (skb)
   └── Передает пакет в стек: netif_receive_skb()

4. Сетевой стек: IP -> TCP
   └── Поиск struct sock по 4-Tuple в хэш-таблице ядра
   └── Помещение skb в очередь sk->sk_receive_queue

5. Триггер пробуждения
   └── Ядро вызывает функцию по указателю: sk->sk_data_ready(sk)
```

## 4. Внутреннее устройство `epoll`

`epoll` — это реактивный механизм ядра, работающий по модели **готовности (Readiness Notification)**. В отличие от `select`/`poll`, он не требует передачи списка опрашиваемых сокетов из User Space в Kernel Space при каждом вызове.

### Структуры данных `struct eventpoll`

При вызове `epoll_create1()` ядро аллоцирует структуру `struct eventpoll`:

```c
/* fs/eventpoll.c */
struct eventpoll {
    wait_queue_head_t     wq;       // Очередь потоков приложения, заснувших в epoll_wait()
    
    // 1. Все сокеты на мониторинге (O(log N) вставка/удаление/поиск)
    struct rb_root_cached rbr;      // Красно-черное дерево (содержит узлы struct epitem)

    // 2. Только готовые к I/O сокеты (O(1) обход)
    struct list_head      rdllist;  // Двусвязный список готовых событий
};
```

Каждое добавление сокета создает связующий узел — **`struct epitem`**:

```c
struct epitem {
    struct rb_node        rbn;      // Узел в красно-черном дереве rbr
    struct list_head      rdllink;  // Узел в списке готовых rdllist
    struct epoll_filefd   ffd;      // Отслеживаемый socket fd
    struct eventpoll     *ep;       // Ссылка на родительский eventpoll
    struct epoll_event    event;    // Маска отслеживаемых событий (EPOLLIN, EPOLLOUT...)
};
```

---

### Механика работы системных вызовов `epoll`

```
epoll_ctl(ADD) ───> 1. Вставляет epitem в RB-дерево (rbr)
                   2. Вешает коллбэк ep_poll_callback() в очередь сокета sk->sk_sleep

Сетевой пакет  ───> 3. Кладет данные в sk_receive_queue
                   4. Дергает sk->sk_data_ready() ──> ep_poll_callback()

ep_poll_callback ─> 5. Добавляет epitem сокета в список rdllist (Ready List)
                   6. Будит поток, спящий в epoll->wq

epoll_wait()   ───> 7. Забирает готовые дескрипторы из rdllist за O(K)
```

1. **`epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event)`:**
   * Добавляет дескриптор в красно-черное дерево `rbr`.
   * Берет очередь ожидания сокета `sk->sk_sleep` и привязывает туда системный коллбэк ядра **`ep_poll_callback`**.
2. **Срабатывание прерывания:**
   * Когда пакет ложится в `sk_receive_queue`, вызывается `sk->sk_data_ready()`.
   * Эта функция запускает привязанный ранее `ep_poll_callback`.
   * `ep_poll_callback` берет данный сокет (`epitem`) и помещает его в двусвязный список готовых сокетов **`rdllist`**.
   * Если в очереди `eventpoll->wq` есть спящий поток приложения, ядро переводит его в состояние `RUNNABLE`.
3. **`epoll_wait(epfd, events, maxevents, timeout)`:**
   * Проверяет список `rdllist`.
   * Если он пуст — поток засыпает на очереди `epoll->wq`.
   * Если в `rdllist` есть элементы — ядро копирует события в пользовательский массив `events`. Сложность — **$O(K)$**, где $K$ — число активных сокетов (независимо от общего числа $N$ соединений на мониторинге).

## 5. Флаги и режимы: `EPOLLIN`, `EPOLLOUT`, LT vs ET

### `EPOLLIN` vs `EPOLLOUT`

* **`EPOLLIN` (Чтение):** срабатывает, когда в `sk_receive_queue` есть байты для `read()`, когда удаленная сторона прислала `FIN` (результат `read() == 0`), либо когда на слушающем сокете появилось готовое подключение для `accept()`.
* **`EPOLLOUT` (Запись):** срабатывает, когда в буфере отправки `sk_write_queue` освободилось место для записи (пришел `ACK` от клиента) или завершился неблокирующий `connect()`.

---

### Паттерн оптимистичной записи (Optimistic Write)
Никогда не держите `EPOLLOUT` включенным постоянно в режиме Level-Triggered: пустой буфер отправки будет генерировать события непрерывно, вызывая 100% утилизацию CPU.

**Алгоритм:**
1. Выполнить `write(fd, data, len)` напрямую, без регистрации в `epoll`.
2. Если `write()` вернул меньше байт, чем нужно, или завершился с ошибкой `EAGAIN` / `EWOULDBLOCK`:
   * Сохранить неотправленный остаток в буфер приложения в памяти процесса.
   * Зарегистрировать сокет в `epoll` с флагом **`EPOLLOUT`** через `epoll_ctl(MOD)`.
3. Когда `epoll_wait()` сообщит о готовности к записи:
   * Дописать оставшиеся данные через `write()`.
   * Как только весь остаток ушел — **немедленно снять флаг `EPOLLOUT`**, вернув только `EPOLLIN`.

---

### Level-Triggered (LT) vs Edge-Triggered (ET)

| Критерий | Level-Triggered (`LT`, дефолт) | Edge-Triggered (`ET`, флаг `EPOLLET`) |
| :--- | :--- | :--- |
| **Условие генерации** | Генерирует событие на каждом вызове `epoll_wait`, **пока буфер не пуст**. | Генерирует событие **только при изменении состояния** (появление новых данных в пустом буфере). |
| **Поведение при неполном чтении** | Если вычитано 50 байт из 100, `epoll_wait` проснется на следующей итерации снова. | Если вычитано 50 байт из 100, `epoll_wait` **заснет навсегда**, пока не придет совершенно новый сетевой пакет. |
| **Требование к чтению** | Можно читать фиксированными кусками за один `read()`. | **Обязателен цикл вычитки:** `while (true) { read(); }` до получения ошибки `EAGAIN` / `EWOULDBLOCK`. |
| **Производительность** | Больше системных вызовов ядра. | Минимальный оверхед, используется в высоконагруженных серверах (Nginx). |
