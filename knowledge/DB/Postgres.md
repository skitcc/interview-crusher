## 1. База данных vs Схема vs Таблица

Иерархия объектов в PostgreSQL строится так:
**Кластер $\to$ База данных $\to$ Схема $\to$ Таблица**

* **Кластер (Cluster):** Один запущенный инстанс Postgres (один процесс-демон, слушающий порт 5432). Обслуживает одну директорию с файлами на диске (`PGDATA`).
* **База данных (Database):** Полная логическая изоляция. 
  * Содержит своих пользователей и права.
  * ⚠️ *Нельзя сделать простой `JOIN` между таблицами двух разных баз данных* в одном запросе (для этого нужны костыли вроде `dblink` или `postgres_fdw`).
* **Схема (Schema):** Пространство имен (namespace) **внутри** одной базы данных.
  * Нужна для логической группировки (например, схемы `public`, `billing`, `analytics`).
  * Таблицы из разных схем **легко объединяются в одном запросе**: 
    `SELECT * FROM billing.orders JOIN public.users ON ...;`
* **Таблица (Table):** Физический набор строк и колонок, принадлежащий конкретной схеме.

## 2. Почему обращение к диску — это ОЧЕНЬ долго?

Разница в скоростях между CPU/ОЗУ и диском колоссальна:

| Уровень | Задержка (Latency) | Наглядная аналогия (если 1 такт CPU = 1 сек) |
| :--- | :--- | :--- |
| **Регистры CPU / L1 кэш** | ~0.5 – 1 нс | 1 секунда |
| **ОЗУ (RAM)** | ~50 – 100 нс | ~1.5 минуты |
| **NVMe SSD (Чтение 4КБ)** | ~10 – 50 мкс (микросекунд) | **~5 – 10 дней** |
| **HDD (Магнитный диск)** | ~5 – 10 мс (миллисекунд) | **~3 – 4 месяца** |

### Физические причины тормозов диска:
1. **HDD:** Механика. Физическая головка должна переместиться на нужную дорожку, а шпиндель диска — повернуться нужным сектором.
2. **SSD:** Механики нет, но чтение идет через контроллер и шину (PCIe/SATA). Память NAND читается только блоками, требуется трансляция адресов в FTL (Flash Translation Layer).
3. **Оверхед ОС:** Чтение с диска требует **системного вызова ядра (syscall `read`)**, переключения контекста процессора из User Space в Kernel Space, работы драйвера и прерываний контроллера (DMA). 
> *Итог:* Чтение даже из быстрого SSD в **100–500 раз медленнее**, чем чтение из оперативной памяти.

## 3. Что стоит поверх TCP при запросе к БД?

Когда Go вызывает `db.Query()`, данные идут не голым текстом. Поверх TCP работает **PostgreSQL Frontend/Backend Protocol (версия 3.0)** — это бинарный протокол прикладного уровня (L7).

### Фазы работы протокола:
* **Подключение:** TCP 3-way handshake $\to$ TLS Handshake $\to$ `StartupMessage` $\to$ Аутентификация (SCRAM-SHA-256 / MD5) $\to$ `ReadyForQuery`.
* **Запрос (Extended Query Protocol в Go):**
  1. `Parse (P)` — клиент шлет SQL-шаблон с плейсхолдерами `$1, $2`. Сервер компилирует его в `prepared statement`.
  2. `Bind (B)` — клиент шлет конкретные параметры/значения.
  3. `Execute (E)` — команда серверу выполнить запрос.
  4. `Sync (S)` — закрытие транзакционного блока.
* **Ответ сервера:**
  * Сообщения `RowDescription (T)`: метаданные колонок (имена, типы данных `int4`, `varchar`).
  * Сообщения `DataRow (D)`: сырые бинарные байты значений строк.
  * `CommandComplete (C)`: статус выполнения (`SELECT 1`).
  * `ReadyForQuery (Z)`: бэкенд готов принимать следующий запрос.

## 4. Как Postgres хранит данные (Краткий базис)

1. **Страницы по 8 КБ (Pages):** Таблица на диске — это файл, нарезанный на куски по 8 КБ. Данные всегда читаются и пишутся только целыми страницами.
2. **`ctid` (Tuple ID):** Физический адрес строки: `(номер_страницы, индекс_внутри_страницы)`, например `(0, 3)`.
3. **`Shared Buffers`:** Кэш в ОЗУ самого Postgres.
4. **`OS Page Cache`:** Кэш файлов в ОЗУ ядра Linux.

## 5. Полный путь выполнения `SELECT * FROM users WHERE age = 30`

### СЦЕНАРИЙ А: Индекса по колонке `age` НЕТ (Sequential Scan)

1. **Go:** `rows, err := db.Query(ctx, "SELECT * FROM users WHERE age = $1", 30)` сериализуется в байты wire-протокола и улетает в TCP-сокет.
2. **Postgres Backend:** Вычитывает байты из сокета, планировщик строит план: **`Seq Scan on users`**.
3. **Чтение данных (в цикле по всей таблице):**
   * Postgres смотрит страницу №0:
     * Есть в `shared_buffers`? Нет $\to$ Запрос к ядру ОС (`pread`).
     * Есть в `OS Page Cache`? Нет $\to$ Контроллер SSD поднимает 8 КБ с диска в память.
   * Страница №0 загружена в ОЗУ.
   * Исполнитель перебирает все кортежи страницы №0: сверяет `MVCC` (жива ли строка) и условие `age == 30`.
   * **Повторяет это для страницы №1, №2 ... №100 000** (тянет весь объем таблицы с диска в память).
4. **Сеть:** Найденные совпадения пакуются в пакеты `DataRow` и шлются в TCP-сокет.
5. **Go:** Драйвер (`pgx`) читает байты из сокета, `rows.Scan()` аллоцирует структуры Go в памяти.

> 🔴 **Итог без индекса:** Прочитано 100 000 страниц (гигабайты I/O). Загружен диск, забит CPU. Время: **секунды**.

---

### СЦЕНАРИЙ Б: Есть B-Tree индекс `CREATE INDEX idx_users_age ON users(age)`

1. **Go:** Отправляет точно такой же запрос.
2. **Postgres Backend:** Планировщик видит условие `age = 30` и выбирает план **`Index Scan using idx_users_age`**.
3. **Поиск по дереву индекса (отдельный файл на диске):**
   * Считывается **Root Page** индекса (обычно уже горячая в `shared_buffers`). Значение `30` направляет поиск в нужную дочернюю ветку.
   * Считывается **Internal Page**.
   * Считывается **Leaf Page** индекса. В листе найдена запись: ключ `30` и указатель **`ctid = (42, 5)`**.
4. **Точечное чтение таблицы:**
   * Postgres идет **строго в страницу таблицы №42**.
   * Если страницы №42 нет в памяти — с диска читаются **всего одни эти 8 КБ**.
   * Извлекается строка со смещением `5`, проверяется видимость по `MVCC`.
5. **Сеть и Go:** Результат возвращается в приложение точно так же через `DataRow`.

> 🟢 **Итог с индексом:** Прочитано 3-4 страницы индекса + 1 страница таблицы (всего 30-40 КБ данных вместо гигабайт). Время: **доли миллисекунды**.

## 7. OLTP vs OLAP: Транзакции против Аналитики

> [!abstract] Главное отличие в одной фразе
> * **OLTP** — про **настоящее**: быстрая точечная работа со строками в реальном времени (CRUD, заказы, платежи).
> * **OLAP** — про **прошлое**: тяжелые аналитические расчеты по колонкам над миллиардами исторических записей (отчеты, графики).

---

### Сравнительная таблица

| Критерий | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |
| :--- | :--- | :--- |
| **Основная цель** | Быстрый отклик бизнес-операций | Поиск инсайтов, агрегации, бизнес-аналитика |
| **Характер запросов** | Простые `INSERT`, `UPDATE`, `SELECT` по ID | Сложные `SUM`, `AVG`, `COUNT`, `GROUP BY` |
| **Объем выборки** | Единичные строки (килобайты) | Миллионы/миллиарды строк (гигабайты) |
| **Ориентация данных** | **Построчная (Row-oriented)** | **Поколоночная (Column-oriented)** |
| **Схема данных** | Нормализованная (3NF, без дублей) | Денормализованная («Звезда», плоские таблицы) |
| **Примеры СУБД** | **PostgreSQL**, MySQL, Oracle | **ClickHouse**, Snowflake, BigQuery |

---

### Физика хранения: Строки vs Колонки

```text
Таблица: [id, user_id, amount]

Построчно (Postgres / OLTP):
Диск: [1, usr_A, 500] [2, usr_B, 1500] [3, usr_C, 200]
⚠️ Чтобы посчитать AVG(amount), база тянет с диска ВСЕ строки целиком вместе с user_id.

Поколоночно (ClickHouse / OLAP):
Файл id:     [1, 2, 3]
Файл user:   [usr_A, usr_B, usr_C]
Файл amount: [500, 1500, 200]
✅ Чтобы посчитать AVG(amount), база читает ТОЛЬКО файл amount.bin (I/O в разы меньше + сжатие однотипных данных в 5-10 раз сильнее).
```

### Архитектурный паттерн в продакшене

> [!danger] Золотое правило Highload
> **Никогда не пускать аналитиков и тяжелые дашборды в боевую OLTP-базу (Postgres)**, иначе они забьют память, диск и CPU, заблокировав оформление заказов пользователями.

**Стандартная связка:**
1. Пользователь делает заказ $\to$ пишем в **PostgreSQL (OLTP)** (важен ACID и ответ за 10 мс).
2. Изменения через **Change Data Capture (Debezium / Kafka)** асинхронно переливаются в **ClickHouse (OLAP)**.
3. Аналитики строят графики и считают метрики в ClickHouse за доли секунды над терабайтами данных.
