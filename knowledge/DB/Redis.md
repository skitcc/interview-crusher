### 1. AOF и RDB (сохранение данных на диск)

По умолчанию Redis держит всё в RAM. Чтобы не потерять данные при перезагрузке, есть два механизма:

*   **RDB (Redis Database Backup):**
    *   **Как работает:** периодический снимок (снапшот) всей памяти на диск в один бинарный файл (например, раз в 5 минут, если было > 100 изменений).
    *   **Плюсы:** база стартует очень быстро, компактный размер файла.
    *   **Минусы:** при внезапном падении теряются данные за последние минуты (всё, что было после последнего снапшота).
*   **AOF (Append Only File):**
    *   **Как работает:** лог каждой операции записи (`SET`, `HSET` и т.д.). Каждая команда дописывается в конец файла.
    *   **Плюсы:** минимальный риск потери данных (обычно теряется не более 1 секунды).
    *   **Минусы:** файл разрастается, восстановление базы занимает больше времени. (Redis умеет делать фоновое сжатие лога — *AOF rewrite*).
*   **Практика:** Чаще всего используют **гибрид** (RDB + AOF) — база стартует быстро из снапшота RDB и докатывает свежие операции из хвоста AOF.

### 2. Pipelining (Батч-обработка)

*   **Проблема:** обычно запрос к Redis работает по схеме: *запрос → ожидание ответа по сети (RTT) → ответ*. Если нужно сделать 10 000 вставок, 95% времени уходит на сетевые задержки.
*   **Pipelining:** клиент отправляет сразу пачку из N команд в один сокет, **не дожидаясь ответа на каждую**, а затем читает один общий ответ со всеми результатами.
*   **Результат:** скорость возрастает в десятки раз (сокращается сетевой оверхед).
*   *Важно:* Pipelining **не гарантирует атомарность** (команды из пайплайна могут перемешаться с командами другого клиента). Если нужна изоляция — используют `MULTI / EXEC` (транзакции) или Lua-скрипты.

### 3. Топологии: Main (Master-Replica) и Sentinel

*   **Main-Replica (Master-Slave):**
    *   Есть один узел **Main (Master)**, куда идут все записи (и можно читать).
    *   Есть одна или несколько **Replicas**, которые асинхронно копируют данные с Main и отдают только чтение.
    *   *Зачем:* масштабирование чтения и резервная копия.
    *   *Минус:* если Main падает, переключать трафик на реплику нужно вручную.
*   **Sentinel (Страж):**
    *   Это надстройка над Main-Replica для **высокой доступности (High Availability)**.
    *   Sentinel — это отдельный легковесный процесс (обычно ставят 3 штуки для кворума).
    *   *Что делает:* пингует узлы. Если Main упал, стражи договариваются, автоматически назначают одну из реплик новым Main, а клиентам сообщают новый адрес.

### 4. Типы данных

1.  **String:** Базовый тип (текст, JSON-строка, число или бинарные данные до 512 МБ). Команды: `SET`, `GET`, `INCR` (атомарный счетчик).
2.  **Hash:** Словарь внутри ключа (`field: value`). Идеально ложится на объекты (например, пользователь: `name`, `email`, `age`). Команды: `HSET`, `HGET`.
3.  **List:** Двусвязный список. Быстрая вставка в начало и конец. Подходит для очередей (FIFO) и стеков (LIFO). Команды: `LPUSH`, `RPOP`, `LRANGE`.
4.  **Set:** Множество неупорядоченных **уникальных** элементов. Умеет быстро пересекать множества (`SINTER`), объединять, проверять наличие. Команды: `SADD`, `SISMEMBER`.
5.  **Sorted Set (ZSet):** Множество уникальных строк, но у каждого элемента есть вес (`score`). Автоматически отсортировано. Идеально для лидербордов, систем рейтинга и очередей с приоритетом. Команды: `ZADD`, `ZRANGE`.
6.  *Специализированные:* **Bitmap** (битовые маски, учет онлайна), **HyperLogLog** (приблизительный подсчет миллионов уникальных посещений в 12 КБ памяти), **Geospatial** (координаты, поиск объектов рядом).

### 5. Redis Streams

Это структура данных в виде **append-only лога** (упрощенный аналог Apache Kafka прямо внутри Redis).

*   **Как работает:**
    *   Сообщения пишутся в конец с уникальным ID (по умолчанию: `timestamp-seq`, например `1678900000000-0`).
    *   Сообщения **не удаляются** после прочтения (в отличие от `Pub/Sub` или `RPOP` из списков). Их можно перечитывать заново с любой точки времени.
*   **Consumer Groups (Группы потребителей):**
    *   Позволяет масштабировать обработку: несколько воркеров подключаются к одной группе, и Redis распределяет разные сообщения разным воркерам.
    *   **Гарантия доставки:** воркер читает сообщение и обязан отправить подтверждение (`XACK`).
    *   Если воркер упал и не сделал `ACK`, сообщение зависает в списке PEL (Pending Entries List), и другой воркер может перехватить его (`XCLAIM`) и доделать работу.
*   **Зачем нужен:** надёжные очереди задач, шина событий (Event Sourcing), сбор метрик и логов.
