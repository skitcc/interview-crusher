# ACID: Атомарность, Согласованность, Изоляция

Подготовка тестовой таблицы для примеров:
```sql
DROP TABLE IF EXISTS example;
CREATE TABLE example (
    id SERIAL PRIMARY KEY,
    val INTEGER UNIQUE
);
INSERT INTO example (val) VALUES (10);
```

---

## 1. Атомарность (Atomicity)

> [!abstract] Определение
> Все операции внутри транзакции выполняются как единое целое: **либо всё, либо ничего**. Если падает хотя бы один запрос, все предыдущие изменения транзакции откатываются.

```sql
BEGIN;
INSERT INTO example (val) VALUES (20);
-- Допустим, следующая строка вызывает ошибку деления на ноль или нарушение ключа:
INSERT INTO example (val) VALUES ('не число'); 
-- Вся транзакция переходит в статус aborted
ROLLBACK; -- Данные со значением 20 в базу не попадут
```

---

## 2. Согласованность (Consistency)

> [!abstract] Определение
> Транзакция переводит базу данных из одного **корректного** состояния в другое **корректное** состояние. 
> 
> Никакие правила, внешние ключи (`FOREIGN KEY`), ограничения уникальности (`UNIQUE`), проверки (`CHECK`) или бизнес-инварианты не могут быть нарушены.

```sql
-- Если val объявлен как UNIQUE:
BEGIN;
INSERT INTO example (val) VALUES (10); -- Ошибка: val=10 уже есть
-- СУБД защищает целостность и не дает сохранить некорректные данные
ROLLBACK;
```

---

## 3. Изоляция (Isolation)

Определяет, насколько изменения, сделанные одной транзакцией, видимы другим параллельным транзакциям.

### Уровни изоляции и аномалии

| Уровень изоляции | Грязное чтение *(Dirty read)* | Неповторяющееся чтение *(Non-repeatable read)* | Фантомное чтение *(Phantom read)* | Аномалия сериализации *(Write Skew)* |
| :--- | :---: | :---: | :---: | :---: |
| **Read Uncommitted** | ❌ *(в PG нет)* | ❌ | ❌ | ❌ |
| **Read Committed** | ✅ Защищает | ❌ | ❌ | ❌ |
| **Repeatable Read** | ✅ Защищает | ✅ Защищает | ✅ Защищает *(в PG)* | ❌ |
| **Serializable** | ✅ Защищает | ✅ Защищает | ✅ Защищает | ✅ Защищает |

---

### 3.1. Read Uncommitted

> [!danger] Аномалия: Грязное чтение (Dirty Read)
> Транзакция читает данные, которые были изменены другой транзакцией, но **еще не закоммичены** (и могут быть откатаны через `ROLLBACK`).

> [!note] Особенность PostgreSQL
> В PostgreSQL уровень `READ UNCOMMITTED` формально можно задать, но **под капотом он работает как `READ COMMITTED`**. Из-за архитектуры MVCC (многоверсионности) PostgreSQL физически не умеет отдавать незакоммиченные строки другим сессиям.

```sql
-- Сессия 1:
BEGIN;
INSERT INTO example (val) VALUES (99);
-- COMMIT пока не делаем!

-- Сессия 2:
BEGIN;
SELECT * FROM example WHERE val = 99;
-- Ничего не вернет, так как грязное чтение невозможно
```

---

### 3.2. Read Committed (Чтение зафиксированных данных)

> [!info] Поведение по умолчанию в PostgreSQL
> Каждый отдельный SQL-запрос внутри транзакции видит снимок данных на **момент старта этого конкретного запроса** (а не всей транзакции).

Не защищает от:
1. **Неповторяющегося чтения**: одна и та же строка возвращает разные значения при повторном `SELECT`.
2. **Фантомного чтения**: повторный `SELECT` с тем же условием возвращает **новые** строки, вставленные другой параллельной транзакцией.

```sql
-- Шаг 1 (Сессия 1):
BEGIN;
SELECT COUNT(*) FROM example; -- Результат: например, 1 строка

    -- Шаг 2 (Сессия 2, параллельно):
    BEGIN;
    INSERT INTO example (val) VALUES (20);
    COMMIT; -- Закоммитили новую строку!

-- Шаг 3 (Сессия 1):
SELECT COUNT(*) FROM example; -- Результат: уже 2 строки (Фантомное чтение!)
COMMIT;
```

---

### 3.3. Repeatable Read (Повторяемое чтение)

> [!tip] Как работает в PostgreSQL
> Снимок (*snapshot*) данных фиксируется **один раз на всю транзакцию** — в момент выполнения первого запроса. Все последующие запросы транзакции работают строго с этим неизменным снимком.
> 
> *В PostgreSQL этот уровень защищает как от неповторяющегося, так и от фантомного чтения.*

```sql
-- Шаг 1 (Сессия 1):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM example; -- Результат: 1 строка

    -- Шаг 2 (Сессия 2, параллельно):
    BEGIN;
    INSERT INTO example (val) VALUES (30);
    COMMIT;

-- Шаг 3 (Сессия 1):
SELECT COUNT(*) FROM example; -- Результат: по-прежнему 1 строка!
SELECT * FROM example;        -- Строку val=30 мы не увидим, пока не завершим транзакцию
COMMIT;
```

---

### 3.4. Serializable (Сериализуемость)

> [!warning] От чего НЕ спасает Repeatable Read?
> `REPEATABLE READ` защищает от чтения «чужих» изменений, но **не защищает от логических аномалий записи**, таких как **Write Skew (перекос записи)**. 
> 
> Это ситуация, когда две транзакции читают одни и те же данные, принимают решение на основе прочитанного, а затем вставляют/обновляют разные строки, нарушая общий инвариант системы.

> [!success] Суть Serializable
> Гарантирует, что параллельное выполнение нескольких транзакций даст **абсолютно такой же результат, как если бы они выполнялись строго по очереди**. СУБД отслеживает зависимости чтения и записи (SSI — *Serializable Snapshot Isolation*) и принудительно отменяет конфликтную транзакцию.

#### Пример: Аномалия Write Skew (Дежурные врачи)

> **Бизнес-правило:** В больнице на дежурстве должен оставаться **хотя бы один врач**.

```sql
-- Подготовка таблицы дежурств:
CREATE TABLE doctors (
    id SERIAL PRIMARY KEY,
    name TEXT,
    on_call BOOLEAN -- true = на дежурстве
);

INSERT INTO doctors (name, on_call) VALUES 
('Доктор Хаус', true),
('Доктор Ватсон', true);
```

##### ❌ Что произойдет в `REPEATABLE READ`:
1. **Врач 1** хочет уйти. Транзакция 1 проверяет: `SELECT count(*) FROM doctors WHERE on_call = true;` (Ответ: 2. Всё ок, можно уйти).
2. **Врач 2** одновременно хочет уйти. Транзакция 2 проверяет: `SELECT count(*) FROM doctors WHERE on_call = true;` (Ответ: 2. Всё ок, можно уйти).
3. **Транзакция 1**: `UPDATE doctors SET on_call = false WHERE name = 'Доктор Хаус'; COMMIT;`
4. **Транзакция 2**: `UPDATE doctors SET on_call = false WHERE name = 'Доктор Ватсон'; COMMIT;`
> **Итог в Repeatable Read:** Обе транзакции успешно закоммитились. На дежурстве осталось **0 врачей**. Бизнес-правило нарушено!

---

##### ✅ Как эту проблему решает `SERIALIZABLE`:

```sql
-- Окно 1 (Врач 1):
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE on_call = true; -- Видит 2 врачей
UPDATE doctors SET on_call = false WHERE name = 'Доктор Хаус';

-- Окно 2 (Врач 2, параллельно):
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE on_call = true; -- Видит 2 врачей
UPDATE doctors SET on_call = false WHERE name = 'Доктор Ватсон';

-- Окно 1:
COMMIT; -- Успешно зафиксировано!

-- Окно 2:
COMMIT;
```

> [!danger] Результат в Окне 2:
> PostgreSQL обнаруживает цикл зависимостей между чтением и записью и аварийно прерывает вторую транзакцию:
> ```text
> SQL Error [40001]: ERROR: could not serialize access due to read/write dependencies among transactions
> Detail: Reason code: Canceled on identification as a pivot, during commit attempt.
> Hint: The transaction might succeed if retried.
> ```
> База спасла инвариант: дежурить остался хотя бы один врач!

> [!tip] Правило разработки для Serializable
> Если в приложении используется уровень `SERIALIZABLE`, код приложения **обязан быть готов перехватывать ошибку `40001`** и автоматически перезапускать упавшую транзакцию заново (*retry loop*).


## Durability

Это значит, что после окончания транзакции данные записались на жесткий диск и в случае внезапного выключения электричества/сбоя данные все равно останутся в базе данных и не потеряются.
