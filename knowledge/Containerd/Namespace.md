
[[Контейнеризация]]

Пространство имён (англ. namespace) — это механизм ядра Linux, обеспечивающий изоляцию процессов друг от друга. Работа по его реализации была начата в версии ядра 2.4.19. На текущий момент в Linux поддерживается шесть типов пространств имён:


Контейнеры в Linux — это не виртуальные машины с собственным ядром и эмуляцией «железа». Контейнер — это **обычный процесс хост-системы**, работающий на общем ядре Linux, но ограниченный двумя ключевыми подсистемами:
1. **cgroups (Control Groups)** — контролирует **ресурсы** (лимиты по CPU, RAM, дисковому I/O, сети).
2. **namespaces (Пространства имён)** — контролирует **видимость** (какие системные ресурсы процесс видит вокруг себя).

---

## 1. Предыстория: почему `chroot()` оказалось недостаточно?

Первая попытка изолировать окружение процесса появилась в 1979 году в UNIX Version 7 — системный вызов `chroot()` (*change root*).

* **Принцип работы:** процесс «запирается» в отдельной директории, которая объявляется для него корнем файловой системы (`/`).
* **В чём проблема:** `chroot()` изолирует **только файлы**. Процесс внутри chroot:
  * видит процессы хоста в общем дереве и может завершить их через `kill`;
  * использует общий сетевой стек (не может открыть уже занятый на хосте порт 80);
  * использует глобальное имя хоста (`hostname`);
  * использует глобальные таблицы пользователей: root внутри chroot остаётся root'ом на всей машине и может легко сбежать из окружения.

Для полноценной изоляции ядру Linux потребовался механизм разделения глобальных таблиц ядра — **namespaces**.

## 2. Анатомия системного вызова `clone()` и управление стеком

В Linux есть три системных вызова для порождения задач: `fork()`, `vfork()` и `clone()`. Все они под капотом обращаются к функции ядра `kernel_clone()` (ранее `_do_fork()`), но интерфейс `clone()` спроектирован принципиально иначе.

### Чем `fork()` отличается от `clone()`?

| Критерий | `fork()` | `clone()` |
| :--- | :--- | :--- |
| **Что создаёт** | Только полноценный дочерний процесс. | Любую сущность: от потока (thread) до изолированного контейнера. |
| **Память** | Создаёт копию виртуальных страниц (Copy-on-Write). | Настраивается флагами: общая память (`CLONE_VM`) или раздельная. |
| **Точка входа** | Возвращает управление в ту же точку кода (проверяем `pid == 0`). | Запускает **новую указанную функцию** (`int (*fn)(void *)`). |
| **Стек** | Наследует текущий стек родителя. | **Требует явного выделения памяти под стек.** |

### Зачем `clone()` требует передавать стек (`child_stack`)?

При использовании `fork()` процессу не нужен новый стек: ядро дублирует таблицы страниц памяти родителя, и потомок начинает выполнение со старым регистром указателя стека (`RSP`).

`clone()` — это универсальный низкоуровневый системный вызов, на котором строятся в том числе системные потоки (библиотека `pthreads`). 
1. **Предотвращение повреждения памяти:** Если `clone()` вызывается для создания потока с флагом `CLONE_VM`, родитель и потомок делят **одну и ту же оперативную память**. Если бы они использовали один стек, одновременные вызовы функций затирали бы адреса возврата и локальные переменные друг друга, приводя к мгновенному `Segmentation fault`.
2. **Обертка glibc:** В glibc `clone()` принимает указатель на функцию `child_fn`. Чтобы ядро и рантайм могли переключить контекст и вызвать эту функцию, процессору с самого первого такта требуется валидная область памяти под фрейм стека (сохранение регистров, аргументов и адреса возврата).

### Почему стек передается со смещением: `child_stack + 1048576`?

В большинстве современных аппаратных архитектур (включая x86, x86-64 и ARM) **стек растёт сверху вниз** — от больших адресов к меньшим:

```text
Младшие адреса                         Старшие адреса
[ 0x1000 ] <--------------------------- [ 0x1FFFF ]
Начало массива                          Конец массива (1 МБ)
(child_stack)                           (child_stack + 1048576)
                                               │
                                               ▼
                                  Здесь должен начинаться стек!
                                  (Вершина стека: регистр RSP)
```

1. Когда мы выделяем массив размером 1 МБ (`1048576` байт):
   * `static char child_stack[1048576];` (в секции BSS программы) или
   * `char *child_stack = malloc(1048576);` (в куче/Heap),
   указатель `child_stack` смотрит на **самый младший адрес** (начало) буфера.
2. Если передать процессору указатель `child_stack`, первая же операция `push` или вызов подпрограммы попытается записать данные по адресу `child_stack - 8`. Это запись в чужую область памяти — программа упадет с ошибкой сегментации.
3. Поэтому мы передаем `child_stack + 1048576` — указатель на конец буфера. По мере работы функции процессор будет уменьшать указатель стека (`RSP`), двигаясь вниз в пределах выделенного массива.

## 3. Системные вызовы для управления Namespaces

Ядро предоставляет три системных вызова для манипуляции пространствами имён:

1. **`clone(fn, stack, flags, arg)`** — создаёт новый процесс и сразу помещает его в указанные флаги пространств имён (`CLONE_NEW*`).
2. **`unshare(flags)`** — выводит *текущий* процесс из пространств имён родителя и помещает его в новые, не создавая потомка.
3. **`setns(fd, nstype)`** — присоединяет текущий процесс к уже существующему пространству имён (так работает команда `docker exec`). В качестве `fd` передается файловый дескриптор из псевдофайловой системы `/proc/<PID>/ns/`.

Каждый тип пространства имён отображается для процесса в псевдокаталоге `/proc/<PID>/ns/`:
```bash
ls -l /proc/$$/ns
# Выведет список ссылок вида:
# pid -> 'pid:[4026531836]'
# uts -> 'uts:[4026531838]'
```
Число в квадратных скобках — идентификатор (inode) конкретного namespace в ядре. Если у двух процессов идентификаторы совпадают, они разделяют один и тот же контекст.

## 4. Разбор ключевых Namespaces с примерами

> **Важно:** Создание большинства пространств имён требует привилегии **`CAP_SYS_ADMIN`**. Все примеры программ, использующие вызовы `clone()` с флагами `CLONE_NEW*`, необходимо запускать от пользователя `root` (через `sudo`).

---

### 4.1 PID Namespace (`CLONE_NEWPID`) — Изоляция процессов

Каждый PID namespace имеет собственное дерево процессов. Процесс, созданный первым в новом PID namespace, получает внутри него **PID 1** (становится аналогом `init` / `systemd` для этого пространства).

#### Практический пример: демонстрация `CLONE_NEWPID`

```c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

// Выделяем 1 МБ памяти под стек потомка в секции BSS
static char child_stack[1048576];

static int child_fn() {
    // Внутри нового пространства имён процесс видит себя как PID 1
    printf("Внутри контейнера: getpid() = %ld\n", (long)getpid());
    return 0;
}

int main() {
    printf("Родительский процесс: PID хоста = %ld\n", (long)getpid());

    // Флаг CLONE_NEWPID — изолирует дерево процессов
    // Флаг SIGCHLD — указывает ядру послать сигнал родителю при завершении потомка (для waitpid)
    pid_t child_pid = clone(child_fn, child_stack + 1048576, CLONE_NEWPID | SIGCHLD, NULL);

    if (child_pid == -1) {
        perror("Ошибка clone");
        exit(EXIT_FAILURE);
    }

    // С точки зрения родительского пространства имён у потомка обычный глобальный PID
    printf("Снаружи (хост видит потомка как): clone() = %ld\n", (long)child_pid);

    // Ожидаем завершения дочернего процесса
    waitpid(child_pid, NULL, 0);
    return 0;
}
```

#### Сборка и запуск:
```bash
gcc -Wall main.c -o pid_ns_demo
sudo ./pid_ns_demo
```

#### Результат выполнения:
```text
Родительский процесс: PID хоста = 4120
Снаружи (хост видит потомка как): clone() = 4121
Внутри контейнера: getpid() = 1
```

#### Почему это происходит (Двойственность PID):
* Процесс существует в ядре в единственном экземпляре, но зарегистрирован сразу в двух таблицах:
  1. В глобальной таблице хоста ему присвоен PID `4121`.
  2. Во вложенной таблице нового пространства имён он стал первым процессом и получил PID `1`.
* **Нюанс с утилитой `ps`:** Если внутри `child_fn` вызвать команду `ps aux`, она всё равно покажет процессы хоста. Причина в том, что `ps` читает состояние не из системных вызовов ядра, а парсит файлы `/proc`. Чтобы `ps` видела только процессы своего контейнера, PID namespace комбинируют с **Mount namespace** и заново монтируют `/proc`.

### 4.2 UTS Namespace (`CLONE_NEWUTS`) — Имя узла (Hostname)

Изолирует системный идентификатор узла (`nodename`) и доменное имя (`domainname`), возвращаемые вызовом `uname()`.

```c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/utsname.h>
#include <sys/wait.h>
#include <unistd.h>

static char child_stack[1048576];

void print_hostname() {
    struct utsname u;
    uname(&u);
    printf("Hostname: %s\n", u.nodename);
}

static int child_fn(void *arg) {
    printf("Потомок до изменения: ");
    print_hostname();

    // Меняем имя хоста (затронет только текущий UTS namespace)
    sethostname("isolated-container", 18);

    printf("Потомок после изменения: ");
    print_hostname();
    return 0;
}

int main() {
    printf("Хост в начале: ");
    print_hostname();

    pid_t child_pid = clone(child_fn, child_stack + 1048576, CLONE_NEWUTS | SIGCHLD, NULL);
    if (child_pid == -1) {
        perror("Ошибка clone");
        exit(EXIT_FAILURE);
    }

    waitpid(child_pid, NULL, 0);

    printf("Хост после завершения потомка: ");
    print_hostname();
    return 0;
}
```

#### Вывод:
```text
Хост в начале: Hostname: my-pc
Потомок до изменения: Hostname: my-pc
Потомок после изменения: Hostname: isolated-container
Хост после завершения потомка: Hostname: my-pc
```

### 4.3 Network Namespace (`CLONE_NEWNET`) — Сетевой стек

Изолирует физические и виртуальные сетевые интерфейсы, таблицы маршрутизации, сокеты и правила фаервола (`iptables`/`nftables`).

Позволяет процессу внутри контейнера привязаться к порту `80`, даже если на хосте порт `80` уже занят веб-сервером.

Связывание изолированного Network namespace с хостом выполняется через виртуальную пару сетевых интерфейсов (`veth pair`), работающую по принципу программного патч-корда:

```bash
# 1. Создаем сетевое пространство имен 'isolated_net'
sudo ip netns add isolated_net

# 2. Создаем пару связанных виртуальных интерфейсов veth0 <-> veth1
sudo ip link add veth0 type veth peer name veth1

# 3. Перемещаем veth1 внутрь isolated_net
sudo ip link set veth1 netns isolated_net

# 4. Назначаем IP-адреса концам виртуального кабеля
sudo ip addr add 10.10.0.1/24 dev veth0
sudo ip link set veth0 up

sudo ip netns exec isolated_net ip addr add 10.10.0.2/24 dev veth1
sudo ip netns exec isolated_net ip link set veth1 up

# 5. Проверяем пинг из изолированного namespace в сторону хоста
sudo ip netns exec isolated_net ping -c 2 10.10.0.1
```

### 4.4 Прочие пространства имён ядра

* **Mount (`CLONE_NEWNS`):** Изолирует таблицу точек монтирования. Позволяет процессу монтировать свои файловые системы (например, собственный `/proc`, изолированный корень через `pivot_root`), не влияя на монтирования хоста.
* **IPC (`CLONE_NEWIPC`):** Изолирует механизмы межпроцессного взаимодействия System V и POSIX (очереди сообщений, семафоры, разделяемую память `shmget`/`shmat`). Процессы в разных IPC namespaces не могут получить доступ к общей памяти друг друга.
* **User (`CLONE_NEWUSER`):** Изолирует диапазоны UID и GID. Позволяет процессору быть `root` (UID 0) внутри своего пространства имён, оставаясь непривилегированным пользователем (UID 1000) на реальном сервере. Единственный namespace, который можно создать без прав `CAP_SYS_ADMIN`.

## 5. Сводная картина: как рождается контейнер

Когда Docker запускает контейнер командой `docker run`:

```text
[ Docker Daemon / containerd / runc ]
                │
                ▼
1. Системный вызов clone():
   CLONE_NEWPID | CLONE_NEWUTS | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWIPC
                │
                ├─► Процесс получает собственный PID 1
                ├─► Процесс получает собственное имя узла (Container ID)
                ├─► Создается пустой сетевой стек (loopback)
                │
2. Настройка окружения:
   ├─ На хосте создается пара veth-интерфейсов, один конец отдается в netns
   ├─ Монтируется изолированная файловая система (overlayfs) через pivot_root
   ├─ Монтируется свежий /proc
   │
3. Ограничение ресурсов:
   └─ PID процесса записывается в cgroup (/sys/fs/cgroup/.../cgroup.procs)
                │
                ▼
4. Вызов execve() -> Запуск вашего приложения (например, Nginx или Python)
```

Контейнер — это иллюзия полной изоляции, созданная ядром за счет скрытия глобальных таблиц через **namespaces** и лимитирования ресурсов через **cgroups**.
